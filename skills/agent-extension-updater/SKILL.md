# Agent 扩展更新（技能与插件）

维护 **skills + plugins** 的版本。**Agent 本体不在本技能范围内**——不检查、不升级、不列入清单；本体升级请走宿主官方入口。默认路径：**自动检查 → 主动确认 → 备份 → 官方渠道更新 → 逐项验证**。不单独维护 MCP，不升级模型或操作系统。

## 何时使用 / 何时不使用

**使用**：用户要求检查更新、更新 skills 或 plugins、做维护巡检；或询问某个扩展的来源是否可信、是否已是最新版、能不能升。

**不使用**：**升级 Agent 本体**（本技能明确不覆盖，请用宿主自己的官方更新入口）；单独升级 MCP 服务、模型、系统或无关软件；只有网页聊天、没有任何本地执行能力时声称"已在本机完成更新"；用户没有提出更新意图时的自动巡检（需按文末方式单独接入）。

## 红线

六条贯穿全文，任何步骤都不得违反：

1. **不猜命令** —— 只用本机 help 或官方文档确认过的命令；核实不了就标"未验证"，绝不编造 `xxx update` 之类的接口。
2. **不静默改动** —— 安装、更新、启用、重启，都必须先拿到用户对**具体项目 + 来源 + 目标版本**的确认。
3. **不掩盖失败** —— 网络失败、检查失败、无法核实，一律如实报告；**不能把检查失败说成"已是最新"**。
4. **不越权** —— 只处理当前宿主和用户明确授权的目录 / profile；不切发行渠道、不自动信任新来源、不降低安全设置。
5. **不破坏** —— 保留本地修改；禁止 `--force` 覆盖、强推、删除未知文件；没有可验证的备份与恢复路径就先停下问用户。
6. **不假装运行** —— skill 是流程指令，不是常驻程序。跳过、取消、无回复都不算批准；一次批准不等于永久授权。

## 第一步：识别宿主，选定适配文档

先认出**承载客户端**——模型名不是客户端名，DeepSeek / GPT 等只是模型，不能代替本地安装器。据下表选定唯一一份适配文档，不要混用其他宿主的命令：

| 观察到 | 宿主 | 适配文档 |
| --- | --- | --- |
| `DSH_HOME`、`~/.dsh`、`dsh` 可执行文件、`resources/app-update.yml` | DeepSeek Harness (DSH) | [references/dsh.md](references/dsh.md) |
| `HERMES_HOME` 环境变量、`hermes` 可执行文件 | Hermes | [references/hermes.md](references/hermes.md) |
| `codex` 可执行文件、`~/.codex` | Codex | [references/codex.md](references/codex.md) |
| `claude` 可执行文件、`~/.claude`、`.claude/skills` | Claude Code | [references/claude-code.md](references/claude-code.md) |
| 都不匹配，或"某模型 + 某个客户端" | 通用宿主 | [references/generic-agent.md](references/generic-agent.md) |

⚠️ `~/.agents/skills` 是**多宿主共享目录**（Codex 与 DSH 都会扫描它），单独出现不足以判定宿主，必须配合上表的其它信号。

同时记录：真实客户端、运行版本、可执行文件真实路径、安装渠道（官方安装器 / 包管理器 / 桌面端 / IDE 扩展 / 源码）、profile、授权目录、可用的交互工具。技能目录与安装方式见 [README.md](README.md)，最终以宿主**当前**官方文档为准。

未安装的平台标"不适用"，无法核实的接口标"未验证"，不自行安装缺失的客户端。

## 第二步：检查并生成清单

**检查模式是只读的**：不安装、不升级、不启用插件、不修依赖、不重启进程、不改更新源。若某个启动器一运行就会自动修环境，先判断副作用；改用只读元数据，或直接报告阻塞（本技能在 Hermes 上就遇到过这类启动器，见适配文档）。

**先跑盘点器**（只读、零依赖、跨宿主）：

```bash
node scripts/inventory.mjs --check-updates   # 联网探测上游；纯本地盘点去掉该参数
node scripts/inventory.mjs --all             # 连"无上游的本地技能"也逐条列出
node scripts/inventory.mjs --json            # 机器可读（便于二次处理）
```

它按宿主列出 **技能 / 插件** 的「实际路径 / 渠道 / 当前版本 / 最新版本 / 状态 / **在哪里更新**」。
自动定位不到宿主目录时用 `--project <目录>` 指定项目根；只处理授权宿主时用 `--hosts dsh,hermes`。
盘点器自己的判定规则与本技能一致：**读不到本机版本时记"检查失败"，绝不因为远端有版本号就报"有更新"**。

范围：**仅 skills 与 plugins**。Agent 本体不在范围内——不检查、不升级、也不列进清单（它由宿主自己的官方渠道维护）。插件若捆绑 MCP 配置或钩子，必须在清单里披露；涉及新权限、认证或外部服务时重新确认。插件自带的 skills 随插件整体管理，不单独覆盖。

对每一项记录：类型、名称、**实际路径**、安装渠道、可信来源、当前版本/提交、目标版本/提交、变更摘要、本地修改、兼容要求、重启需求、证据。状态只能取：

| 状态 | 含义 |
| --- | --- |
| 有更新 | 已确认可信上游且目标版本明确 |
| 已最新 | 已取得上游版本并比较通过 |
| 检查失败 | 网络、权限、命令缺失等导致无法判断（**不是"已最新"**） |
| 无来源 | 找不到可信上游（本地自定义脚本属于此类，跳过） |
| 待适配 | 接口未核实，需要现场查 help 或官方文档 |

要点：

- 包管理器托管的项用对应管理器查询；Git 项先确认仓库根、远端、分支和工作区状态。
- 版本按该渠道的版本规则比较，**不要用字符串排序**；Git 提交用祖先关系判断，分叉状态不自动合并。
- 解析真实路径后去重；跨越授权目录的符号链接、junction 或共享仓库要先扩大范围确认。
- 不要对"单个 skill 所在的大仓库"直接 `git pull`（见 [generic-agent.md](references/generic-agent.md)）。
- 读取变更日志里的最低宿主版本、依赖、权限和迁移要求。

## 第三步：主动发起确认

检查完成后**立即**发起交互，不要等用户再问。使用 [确认模板](templates/confirmation.md)：优先宿主原生表单/确认工具，否则在当前聊天或交互终端询问。

- 确认必须绑定具体名称、来源、安装范围和目标版本；执行前重新检查目标，目标变了就重新确认。
- 只在宿主提供**已验证**的新会话/窗口接口且用户授权时才开独立窗口；不得篡改会话数据库伪造新聊天。
- 后台无法交互时只保存"待确认清单"，不执行更新；无回复不等于同意。

## 第四步：备份与执行

1. 先确认备份目录、磁盘空间和恢复路径，再动手。
2. 逐项备份实际文件、当前提交/版本和必要的来源元数据；保存本地修改，禁止强制覆盖。
3. 备份与报告都要脱敏：不写凭据、个人信息或完整环境配置；敏感备份留在本地并沿用受限权限。
4. 同一实际路径串行更新；发现其他更新进程或锁，等待用户决策，不抢锁。
5. 按依赖顺序执行；**使用该渠道的官方更新机制**，逐项记录退出码。
6. 失败后停止依赖该项的后续更新（无依赖项可继续）；只在恢复方案已获批准且范围可控时恢复，否则保留备份并报告待恢复。
7. 重启需明确授权；如果更新器无法禁止重启，就在开始前确认中断风险。不要在后台启动"可能自我终止、又无法记录结果"的更新命令。

> DSH 的插件操作另有硬约束：`dsh plugin` **要求先完全退出桌面端**。运行中的会话无法满足，因此这类项必须标为"需退出宿主后手动执行"，不能自动跑。

## 第五步：验证与报告

用 [结果模板](templates/report.md) 输出，并分别标注：

- **已验证生效**：读回精确目标的版本/提交，技能 frontmatter 可被宿主发现，插件清单经官方接口验证。
- **已落盘待重启**：文件已换，但运行中的旧进程仍加载旧代码——**旧会话不能证明新版本已生效**。
- 失败 / 跳过 / 检查失败 / 恢复状态。

退出码为 0 不是唯一证据；验证不了就直说。报告要包含备份与日志位置、下一步动作，不编造验证输出。避免需要付费请求或对外写入的自动健康检查。

## 收尾自检

- [ ] 宿主识别正确，只用了这一份适配文档，没有跨宿主套命令。
- [ ] 每个"有更新"都有可信来源 + 具体目标版本；每个失败都标了"检查失败"，没有被写成"已最新"。
- [ ] 用户批准的是具体项目与版本，不是笼统的"都更新"。
- [ ] 每项都有可验证的备份，或已明确说明无法回滚并获得用户决定。
- [ ] 报告区分了"已验证生效"与"已落盘待重启"，没有被当成同一件事。
- [ ] 没有未经批准的重启、安装、启用或更新源变更。

## 持续运行 / 定时任务 / 自动更新开关

本 skill **不是常驻程序**，不会自行定时启动；定时检查要由宿主的调度能力另行接入（DSH 用会话内调度，其他宿主用系统计划任务）。

**默认流程**：定时的任务只做**只读盘点**，产出待确认清单，并按「客户端 + 实际路径 + 目标版本」去重通知。调度器不能交互时**只检查、只排队**。

**可选：自动更新开关**（默认关闭）。打开后，仅执行作用域内且通过完整护栏的独立 Git 扩展更新；当前与目标版本都必须可验证，目标提交需唯一语义版本标签。版本号不能证明行为兼容。Hub、共享仓库子目录及尚未适配的渠道只列待人工处理。规范、不可配置的硬护栏、备份与审计日志见 [references/auto-update.md](references/auto-update.md)。

```bash
node scripts/auto-update.mjs --status     # 看开关状态与作用域
node scripts/auto-update.mjs --enable     # 打开（长期有效，直到 --disable）
node scripts/auto-update.mjs --run        # 执行；开关关闭时直接拒绝
```

护栏要点：**本体永不自动**、需先退出宿主的不动、主版本跃迁不动、盘点失败不动。
**新一轮执行前重新核实开关状态与本地实际状态，过期的批准不可复用。**
